# DVMail Web: проект защищённого веб-клиента

Документ описывает архитектуру и защиту. Секретов, адресов серверов и ключей в нём нет.

## 1. Цель и границы

- Минималистичный веб-клиент к почтовому серверу Stalwart по протоколу JMAP для семьи.
- Только письма: папки, список, чтение, написать и ответить, вложения, поиск.
- Не делаем: календарь, контакты, файлы, чат, ленты.
- Основной принцип: письмо считается враждебным, пока не доказано обратное.

## 2. Что защищаем (угрозы)

- Вредоносное письмо: скрипты, маячки слежения, фишинговые ссылки, опасные вложения.
- Кража сессии или ключей через XSS (внедрение чужого скрипта).
- Взлом серверной части или хоста, на котором она работает.
- Подбор пароля, перехват токена.
- Потеря ключа шифрования пользователем.
- Подмена кода при сборке и выкатке (цепочка поставки).

## 3. Архитектура

- Браузер (React) -> точка входа (nginx) -> серверная часть (NestJS) -> Stalwart (JMAP, только внутри).
- Браузер никогда не обращается к Stalwart напрямую. Серверная часть это посредник (BFF, backend for frontend, «серверная часть для интерфейса»).
- Серверная часть не хранит письма и не видит открытый текст писем и ключей: для ящиков с включённым шифрованием через неё проходит только шифртекст.
- Хранилище сессий: Redis. База данных на первом этапе не нужна (минимум служб).

## 4. Вход и сессии

- Вход через OAuth 2.0 Stalwart (код авторизации с PKCE): пароль и второй фактор вводятся на странице входа Stalwart.
- Токены хранятся на стороне серверной части (зашифрованно). Браузеру выдаётся только сессионная кука: HttpOnly, Secure, SameSite=Strict, префикс __Host-.
- Защита от подделки запросов (CSRF), ограничение попыток входа, срок простоя, выход со всех устройств.
- Открытое решение: наружу придётся показать страницу входа и точки выдачи токена Stalwart (не JMAP и не админку). Альтернатива: собственная форма входа.

## 5. Шифрование и ключи

- Stalwart шифрует новые входящие письма публичным ключом ящика до записи на диск. Письма, пришедшие до включения, остаются открытыми.
- При первой настройке браузер создаёт пару ключей, загружает в Stalwart только публичную часть и включает шифрование.
- Закрытый ключ хранится только у владельца, на устройстве, зашифрованным ключевой фразой. Письма расшифровывает браузер.
- Новое устройство: ключ переносится через QR. Новый браузер создаёт временный ключ и показывает его в QR, телефон шифрует им ключ пользователя и передаёт через сервер, который видит только шифртекст. На обоих экранах показывается одно число подтверждения.
- Бумажный ключ восстановления у каждого пользователя.
- Сейф администратора (решение владельца): копия ключа каждого пользователя, зашифрованная отдельным ключом администратора, который хранится вне серверов (бумага или флешка). Администратор может восстановить любой ключ и читать письма. Пользователям об этом сообщается прямо.
- Что не защищено: письма во время приёма и отправки видны серверу, исходящая очередь хранит письма до отправки, заголовки могут оставаться открытыми (проверить на тестовом ящике).
- Поиск по тексту выполняется на устройстве, после расшифровки.
- Решено: формат S/MIME, библиотека pkijs (BSD-3-Clause, лицензию подтвердить при подключении). Больше собственного кода вокруг сертификатов, поэтому до интерфейса проводится проверка на тестовом ящике: каким способом Stalwart защищает ключ письма и умеет ли браузер его расшифровать.

## 6. Показ писем

- Сначала простой текст. HTML показывается по желанию в изолированной рамке: iframe с sandbox без allow-scripts и без allow-same-origin, содержимое через srcdoc.
- Перед показом HTML очищается санитайзером (DOMPurify): убираются скрипты, формы, встроенные объекты, обработчики событий, ссылки javascript:, внешние стили.
- Внутри рамки политика безопасности default-src 'none': разрешены только встроенные картинки.
- Внешние картинки выключены, включаются вручную для одного письма.
- Ссылки: показывается реальный адрес, предупреждение при несовпадении текста и адреса, rel="noopener noreferrer", очистка отслеживающих параметров.
- Вложения: только скачивание, Content-Disposition: attachment, X-Content-Type-Options: nosniff, без предпросмотра исполняемых типов.

## 7. Защита самого приложения

- Строгая политика CSP без inline-скриптов (nonce), frame-ancestors 'none', Referrer-Policy: no-referrer, Permissions-Policy (камера только для QR), HSTS после стабилизации, COOP и CORP.
- Зависимости: минимум, версии закреплены, npm audit в CI, проверка лицензий. Разрешены MIT, BSD, Apache, MPL; LGPL, GPL и AGPL только после явного решения.
- В репозитории нет секретов и нет ботов.

## 8. Развёртывание

- Репозиторий публичный, ветки dev и main. Защита main: изменения через pull request, обязательные проверки, запрет принудительного пуша.
- Сборка на серверах GitHub, образ Docker в ghcr.io. Домашний сервер сам забирает новый образ по таймеру. Входящих подключений и раннера с доступом к Docker для клиента нет.
- Контейнеры клиента: без привилегий, корневая файловая система только для чтения, без доступа к данным Stalwart, сеть только до JMAP и Redis.
- Аккаунт GitHub защищён вторым фактором (лучше аппаратным ключом).

## 9. Этапы (каждый заканчивается проверенным результатом)

- Этап 0. Репозиторий, CI, заготовка, заголовки безопасности.
- Этап 1. Вход через Stalwart, список папок и писем.
- Этап 2. Чтение: текст, потом HTML в песочнице, потом вложения.
- Этап 3. Написать и отправить.
- Этап 4. Ключи, шифрование, сейф администратора.
- Этап 5. QR-вход и синхронизация ключа.
- Этап 6. Аудит: лицензии, зависимости, набор вредоносных тестовых писем, проверка заголовков.

## Решения по шифрованию (проверено 28.10.2026)

Проверено на Stalwart 0.16.27 на тестовом ящике (ящик и тестовые ключи удалены).

- Формат писем на диске: S/MIME, CMS AuthEnvelopedData (RFC 5083), шифр на ящике Aes256Gcm.
- Ключ письма защищён RSA-OAEP с SHA-256 (маска MGF1 тоже SHA-256). Это умеет WebCrypto в браузере.
- Сертификаты только RSA. EC-сертификат сервер принимает, но шифровать им не может.
- Шифруются тело и вложения. Заголовки (From, To, Subject, Date) остаются открытыми.
- Поиск работает только по заголовкам, по телу зашифрованных писем он ничего не находит.
- Шифруются только письма, сохранённые после включения. Письма, которые клиент сохраняет сам
  (черновики, отправленные), остаются открытыми, пока не включён encryptOnAppend
  (решение откладывается на этап клиента).
- Библиотека pkijs не разбирает AuthEnvelopedData. Разбор пишется самостоятельно на asn1js
  (лицензия BSD-3) и WebCrypto. Прототип проверен на настоящем письме Stalwart: подмена письма
  и чужой ключ отклоняются.
- Получатель выбирается по серийному номеру сертификата; хеш OAEP проверяется явно.

Как загружаются ключи (JMAP, вход под самим ящиком; возможность urn:stalwart:jmap в session
не объявляется, но методы работают):

    x:PublicKey/set          создать ключ (description, key в PEM, emailAddresses)
    x:AccountSettings/set    выбрать ключ и шифр, id объекта singleton:
        encryptionAtRest: { "@type": "Aes256Gcm", "publicKey": "<id ключа>",
                            "encryptOnAppend": false, "allowSpamTraining": false }
