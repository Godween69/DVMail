# Установка DVMail на свой сервер

Пошаговая инструкция: от пустого сервера до работающего веб-клиента на вашем домене. Здесь
только то, что нужно для установки. Как клиент устроен внутри, описано в docs/WEB.md и
docs/DESIGN.md.

В примерах домен ящиков example.com, адрес сайта mail.example.com. Подставьте свои.

## 1. Что получится

    браузер  ->  nginx (HTTPS, порт 443)  ->  контейнер dvmail-web (порт 3000)  ->  Stalwart (HTTP, JMAP)

- Контейнер dvmail-web: сервер NestJS и собранный сайт React в одном образе.
- Stalwart остаётся как есть. Клиент ходит к нему по внутреннему HTTP-адресу, в интернет этот
  адрес выставлять не нужно.
- Клиент ничего не хранит на диске: ни писем, ни паролей. Резервных копий у него нет, все
  данные лежат в Stalwart (копии делаются для Stalwart).

## 2. Что понадобится

- Stalwart 0.16 с готовыми ящиками на вашем домене и включённым JMAP по HTTP.
- Linux-сервер с Docker и Docker Compose (команда docker compose, версия 2 и новее).
- Домен для сайта (mail.example.com) с записью на ваш сервер и сертификатом TLS. Работать без
  HTTPS клиент не будет: cookie входа с префиксом __Host- браузер принимает только по HTTPS.
- Обратный прокси с HTTPS. Ниже пример для nginx.
- Git. Node.js 22 и npm нужны только если вы хотите прогнать тесты до сборки образа (при
  сборке образа Node ставится внутри Docker).

## 3. Шаг 1. Проверить почтовый сервер

Клиент разговаривает со Stalwart по HTTP-листенеру (в настройках Stalwart по умолчанию порт
8080). Убедитесь, что с сервера, где будет работать клиент, этот адрес отвечает и принимает
ваш ящик. Команда спросит пароль (ввод не виден), он не попадёт в историю командной строки:

    curl -s -u hello@example.com http://АДРЕС_STALWART:8080/jmap/session | head -c 300

В ответ должен прийти JSON со словами "capabilities" и "accounts". Если приходит 401, неверен
логин или пароль. Если соединение не устанавливается, адрес или порт недоступны с этого
сервера.

Что важно знать:

- Войти можно только ящиком домена из настройки ALLOWED_DOMAIN. Остальные клиент отклоняет.
- Если у ящика включена двухфакторная защита, входите паролем приложения (создаётся в личном
  кабинете Stalwart под самим ящиком). Основной пароль у такого ящика не сработает.
- Порты самой почты (25, 465, 993) клиенту не нужны. Нужен только HTTP-адрес JMAP.
- Не публикуйте в интернет веб-интерфейс администратора Stalwart. Клиенту он не нужен.

## 4. Шаг 2. Получить код и проверить его

    git clone https://github.com/Godween69/DVMail.git
    cd DVMail
    git checkout main

Необязательная проверка перед сборкой (нужны Node.js 22 и openssl, занимает несколько минут):

    npm ci
    npm test
    npm run licenses

Тесты работают на заглушке Stalwart, настоящий почтовый сервер им не нужен.

## 5. Шаг 3. Собрать образ

Из корня репозитория:

    docker build -f apps/server/Dockerfile -t dvmail-web:1.0.0 .

Сборка идёт в три ступени: инструменты сборки остаются в промежуточных слоях и в итоговый
образ не попадают. Скрипты установки сторонних пакетов отключены (--ignore-scripts).
Процесс в контейнере работает от обычного пользователя node, не от root. Версию в имени
образа выбирайте сами: при обновлении вы будете менять её и сможете вернуться назад.

Проверка, что образ собрался:

    docker image ls dvmail-web

## 6. Шаг 4. Файл compose

Создайте каталог, например /opt/dvmail, и положите в него файл docker-compose.yml:

    # Веб-клиент DVMail. Порт слушает только локальный адрес сервера: наружу отдаёт nginx.
    services:
      web:
        image: dvmail-web:1.0.0
        pull_policy: never               # образ собран локально, из интернета не скачивается
        container_name: dvmail-web
        restart: unless-stopped
        user: "1000:1000"
        read_only: true                  # файловая система только для чтения
        tmpfs: [/tmp]
        cap_drop: [ALL]                  # никаких особых прав
        security_opt: ["no-new-privileges:true"]
        mem_limit: 512m                  # загружаемый файл (до 25 МБ) держится в памяти целиком
        pids_limit: 150
        environment:
          HOST: 0.0.0.0                  # внутри контейнера; наружу порт только на 127.0.0.1 (ниже)
          PORT: "3000"
          STALWART_URL: http://stalwart:8080
          ALLOWED_DOMAIN: example.com
          ALLOWED_ORIGIN: https://mail.example.com
          COOKIE_SECURE: "true"
        ports:
          - "127.0.0.1:8095:3000"        # только локально: дальше его подхватывает nginx
        networks: [mail]
    networks:
      mail:
        external: true                   # общая сеть со Stalwart

Что здесь нужно подогнать под себя:

- ALLOWED_DOMAIN и ALLOWED_ORIGIN обязательны. Значения по умолчанию в коде относятся к
  проекту автора и вам не подойдут. ALLOWED_ORIGIN пишется точно как адрес сайта в браузере:
  схема, домен, без слэша на конце. Иначе все изменяющие запросы будут отклонены.
- STALWART_URL: адрес Stalwart, достижимый из контейнера. Самый простой вариант, когда Stalwart
  тоже запущен в Docker: создайте общую сеть командой docker network create mail, подключите к
  ней контейнер Stalwart и пишите его имя (в примере stalwart). Если Stalwart работает прямо
  на сервере, а не в контейнере, подойдёт адрес шлюза Docker-сети (обычно 172.17.0.1), при
  условии что Stalwart слушает на нём; тогда сеть mail и блок networks не нужны.
- Порт 8095 любой свободный. Он открыт только на 127.0.0.1, поэтому в брандмауэре правила для
  него не нужны.

Запуск:

    cd /opt/dvmail
    docker compose up -d
    docker compose ps

В столбце состояния через полминуты должно быть healthy. Проверка изнутри сервера:

    curl -s http://127.0.0.1:8095/health

Ответ: {"status":"ok"}.

## 7. Шаг 5. HTTPS и nginx

Клиент нужно отдавать наружу только по HTTPS. Сертификат получите привычным для вас способом
(например, certbot). Пример сервера nginx, файл /etc/nginx/conf.d/mail.example.com.conf:

    # Перенаправление с http на https
    server {
        listen 80;
        server_name mail.example.com;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl;
        # HTTP/2 по желанию: в nginx 1.25.1 и новее добавьте строку «http2 on;»
        server_name mail.example.com;

        ssl_certificate     /etc/letsencrypt/live/mail.example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/mail.example.com/privkey.pem;

        # Принудительный https для браузера (включайте, когда убедились, что https работает)
        add_header Strict-Transport-Security "max-age=31536000" always;

        # Обычные запросы: тело небольшое (письмо до 256 КБ)
        client_max_body_size 1m;

        # Загрузка вложений: до 25 МБ на файл, поэтому предел больше и ожидание дольше
        location /api/attachments {
            client_max_body_size 26m;
            proxy_read_timeout 300s;
            proxy_send_timeout 300s;
            proxy_pass http://127.0.0.1:8095;
            include /etc/nginx/dvmail-proxy.conf;
        }

        location / {
            proxy_pass http://127.0.0.1:8095;
            include /etc/nginx/dvmail-proxy.conf;
        }
    }

И общие заголовки прокси, файл /etc/nginx/dvmail-proxy.conf:

    proxy_http_version 1.1;
    proxy_set_header Host $host;
    # Настоящий адрес клиента: ставьте именно $remote_addr, а не $proxy_add_x_forwarded_for.
    # Иначе клиент сможет подделать адрес и обойти ограничение попыток входа.
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;

Проверьте настройку и перечитайте её:

    sudo nginx -t
    sudo systemctl reload nginx

Заголовки безопасности страницы (политику CSP, запрет вставки в чужие рамки, запрет
кэширования и другие) ставит сам клиент, дублировать их в nginx не нужно: двойные заголовки
только мешают.

Если перед вашим nginx стоит ещё один прокси, он тоже должен передавать настоящий адрес
клиента. Клиент доверяет заголовку X-Forwarded-For только от адресов локальной сети и
loopback; от внешних адресов заголовок игнорируется.

## 8. Шаг 6. Первый вход и проверка

1. Откройте https://mail.example.com и войдите ящиком вашего домена (пароль приложения, если
   включена двухфакторка).
2. Откройте письмо, проверьте папки и счётчики.
3. Напишите себе письмо с небольшим вложением, убедитесь, что оно пришло и вложение
   скачивается.
4. Проверьте большой файл (несколько мегабайт): если загрузка обрывается ошибкой, посмотрите
   раздел «Частые проблемы» (предел размера в nginx).
5. Проверьте на телефоне, в светлой и тёмной теме.

Проверка защиты снаружи (с любого компьютера, пароль не нужен):

    curl -sI https://mail.example.com/ | grep -iE "content-security-policy|strict-transport|x-frame|referrer"

Должны быть видны заголовки политики страницы, HSTS, запрет рамок и политика источника.

## 9. Обновление и откат

Клиент не хранит данные, поэтому обновление простое. Пока идёт перезапуск (несколько секунд),
вошедшие пользователи будут выброшены на страницу входа: сессии живут в памяти процесса.

    cd DVMail
    git pull
    npm ci && npm test                                        # необязательно, но желательно
    docker build -f apps/server/Dockerfile -t dvmail-web:1.1.0 .
    # в /opt/dvmail/docker-compose.yml заменить тег образа на 1.1.0
    cd /opt/dvmail && docker compose up -d

Откат: вернуть прежний тег в docker-compose.yml и снова выполнить docker compose up -d. Старый
образ остаётся на сервере, пока вы его сами не удалите (docker image rm).

Следите за обновлениями зависимостей в репозитории (npm audit) и обновляйте образ, когда
выходят исправления безопасности.

## 10. Админка ящиков (необязательно)

Нужна, если вы хотите создавать и удалять ящики в Stalwart из простой страницы. Это отдельное
приложение, оно не часть webmail и не должно быть доступно из интернета. Как оно защищено и
что умеет, описано в docs/ADMIN.md. Здесь только установка.

1. Подготовьте каталог для секретов, доступный только вам:

        mkdir -p -m 700 /opt/dvmail/secrets

2. Хеш пароля входа в админку (пароль вводится скрытым вводом, не короче 12 символов, сам
   пароль нигде не сохраняется; запускать из каталога репозитория, нужен Node.js):

        node apps/admin/tools/make-password-hash.mjs /opt/dvmail/secrets/admin_password_hash

3. Ключ доступа к API Stalwart. В Stalwart нужен служебный пользователь с ролью администратора
   и ключ API для него (как их создать, написано в документации Stalwart: https://stalw.art).
   Сохраните ключ в файл, не показывая его на экране (команда спросит ключ скрытым вводом):

        read -rs -p "Ключ API Stalwart: " K; echo
        ( umask 077; printf '%s' "$K" > /opt/dvmail/secrets/stalwart_token ); unset K

4. Соберите образ и добавьте службу в тот же docker-compose.yml:

        docker build -f apps/admin/Dockerfile -t dvmail-admin:1.0.0 .

        # в блок services:
          admin:
            image: dvmail-admin:1.0.0
            pull_policy: never
            container_name: dvmail-admin
            restart: unless-stopped
            user: "1000:1000"
            read_only: true
            tmpfs: [/tmp]
            cap_drop: [ALL]
            security_opt: ["no-new-privileges:true"]
            mem_limit: 256m
            environment:
              HOST: 0.0.0.0
              PORT: "3100"
              STALWART_URL: http://stalwart:8080
              ALLOWED_DOMAIN: example.com
              PROTECTED_NAMES: hello           # ящики, которые нельзя удалить и сбросить
            volumes:
              - /opt/dvmail/secrets/stalwart_token:/run/secrets/stalwart_token:ro
              - /opt/dvmail/secrets/admin_password_hash:/run/secrets/admin_password_hash:ro
            ports:
              - "127.0.0.1:3100:3100"          # только локально, в интернет не публиковать
            networks: [mail]

   Файлы секретов должны читаться пользователем контейнера (uid 1000). Если контейнер
   сообщает «Не найден секрет», а у вашего пользователя на сервере другой номер, отдайте файлы
   владельцу 1000: sudo chown 1000 /opt/dvmail/secrets/*, права 600 оставьте.

5. Откройте админку с вашего компьютера по SSH с переадресацией порта (в интернет порт 3100
   не открывайте):

        ssh -L 3100:127.0.0.1:3100 ваш_пользователь@ваш_сервер

   и в браузере адрес http://127.0.0.1:3100. Окно с командой ssh держите открытым, пока работаете. Если вы
   открываете админку по другому адресу или порту, задайте его в переменной ADMIN_HOSTS
   (например, 127.0.0.1:3100), иначе запросы будут отклонены защитой от подмены адреса.

## 11. Справочник настроек

Веб-клиент (переменные окружения контейнера dvmail-web):

- STALWART_URL: внутренний адрес Stalwart. По умолчанию http://dvmail-stalwart:8080.
- ALLOWED_DOMAIN: домен ящиков, с другими войти нельзя. Обязательно задайте свой.
- ALLOWED_ORIGIN: адрес сайта целиком (схема и домен). Обязательно задайте свой.
- COOKIE_SECURE: true по умолчанию. Значение false допустимо только для проверки на своём
  компьютере без HTTPS.
- HOST и PORT: адрес и порт внутри контейнера (в образе заданы 0.0.0.0 и 3000).
- WEB_ROOT: папка собранного сайта (в образе задана).
- DVMAIL_LOG: значение quiet отключает журнал (нужно тестам).

Жёстко заданные пределы (меняются только правкой кода): простой сессии 30 минут, в сумме 12
часов, 8 сессий на ящик, 300 запросов в минуту на сессию, 40 писем в час с ящика, вложения
до 25 МБ. Подробности в docs/WEB.md.

Админка (переменные окружения контейнера dvmail-admin): STALWART_URL, ALLOWED_DOMAIN,
PROTECTED_NAMES, HOST, PORT, ADMIN_HOSTS, STALWART_TOKEN_FILE, ADMIN_PASSWORD_HASH_FILE.
Описание в docs/ADMIN.md.

## 12. Частые проблемы

- Вход не проходит, сообщение про пароль приложения. Проверьте: домен ящика совпадает с
  ALLOWED_DOMAIN; для ящика с двухфакторкой нужен пароль приложения, а не основной пароль;
  команда из шага 1 с этими же данными отвечает.
- После ввода пароля «Запрос отклонён» (403). ALLOWED_ORIGIN не совпадает с адресом, который
  вы открыли в браузере (проверьте схему, домен, отсутствие слэша и порта). Откройте сайт
  по тому же адресу, что указан в настройке.
- Страница открывается, но войти нельзя и cookie не ставится. Сайт открыт не по HTTPS, а
  COOKIE_SECURE равно true. Настройте HTTPS (шаг 5).
- Ошибка 502 при открытии писем. Клиент не может достучаться до Stalwart: проверьте
  STALWART_URL, общую сеть, команду docker compose logs web.
- Вложение не загружается, ошибка 413 от nginx. Пропал блок location /api/attachments с
  client_max_body_size 26m или он не подхватился (nginx -t и reload).
- Загрузка большого файла обрывается по времени. Увеличьте proxy_read_timeout и
  proxy_send_timeout в блоке вложений.
- Ответ 429 «слишком много попыток». Сработало ограничение на подбор пароля (5 неудач на
  пару «сеть и ящик», 20 с одной сети за 15 минут). Подождите. Если блокируются все
  подряд, возможно, прокси не передаёт настоящий адрес клиента (X-Forwarded-For).
- Контейнер unhealthy или перезапускается. Посмотрите журнал: docker compose logs web.
  Частая причина: не хватает прав на чтение при запуске с особым пользователем или на порт
  уже занят другой службой.
- Нужно сбросить забытый пароль ящика. Для этого и существует админка (раздел 10) или
  интерфейс Stalwart.

## 13. Чек-лист безопасной эксплуатации

- Административный интерфейс Stalwart и админка DVMail не доступны из интернета.
- Порты контейнеров открыты только на 127.0.0.1, наружу смотрит только nginx на 443.
- Включён HSTS, сертификат продлевается автоматически.
- Образ пересобирается при выходе исправлений, старые теги убираются через docker image rm.
- Ящики защищены двухфакторкой, вход в клиент идёт паролем приложения.
- В репозитории и в файлах compose нет секретов: ключ API и хеш пароля админки лежат в
  каталоге secrets с правами только для владельца, этот каталог не попадает в git.
